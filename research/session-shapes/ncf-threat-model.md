- Two-gate design (research -> human decision -> build). Gate 1 honoured; build phase then sprawled.
- Outcome: working SSOT-driven pipeline (`build/` emitters) producing a D2 architecture diagram, an Attack Flow STIX bundle, an ATT&CK Navigator heatmap, and a control table. Substantially delivered.

- 11 sub-agents (Agent tool): 8 tool-scouts fired in parallel at seq10-17, then 3 targeted (VSDX search, icon sourcing, ATT&CK-ID verification). This fan-out was the cleanest part of the run.

## Narrative arc
1. Stage 0 intake: restated mission, built GIVEN/ASSUMED infra baseline + open-questions list. Held at the gate as instructed (seq3).
2. Tool survey via 8 parallel scout sub-agents; recommended `diagrams` (mingrammer) for the picture + MITRE Attack Flow for the attack path, verified firsthand against the human's two benchmark JPGs (seq27, seq46).
3. Human corrected assumptions (dev maturity low, VDI hardened, drop Azure Pipelines/PAT assumptions) and pushed back on jargon ("SSOT", "you author this once") — seq28, seq47.

5. Long tail (seq178-267): repeated attempts to get output into the MITRE Attack Flow **Builder GUI** — .afb emitter, STIX import, dangling-edge debugging.

7. Touch-ups: coverage-gap analysis (only 6/10 scenarios visualised) and `attack_flow_render` formatting cleanup.

## Key decisions
- Tool pairing: `diagrams`/D2 (architecture) + MITRE Attack Flow (attack path) + ATT&CK Navigator (heatmap). Correct, benchmark-validated.
- SSOT architecture: one canonical model file, everything regenerated by `build/` emitters (`emit_d2`, `emit_attackflow`, `emit_navigator`, `emit_controls`, `gen_diagram`, `build_all`). Genuinely reusable.
- Renderer pivot D2 > Graphviz, with Graphviz kept as automatic fallback.
- `resvg` over cairosvg/svglib to dodge Windows libcairo failure — good engineering call.
- Decided NOT to build the brittle `.afb` emitter (seq203) — right call, reached late.

## Missteps & dead-ends
- **The Attack Flow Builder rabbit hole (seq178-267, ~1h+).** Sequence: hand-rolled render -> `.afb` emitter idea -> reverse-engineering 184-object canvas geometry (132 anchor/latch primitives) -> STIX import -> dangling-edge debugging -> official-bundle diff -> reading the Builder's own JS source. Root cause was upstream: `mirrorConnections` / layout **commented out** in the Builder (seq267), confirmed by GitHub issue #149 (seq268). Effort spent making a known-broken GUI render never paid off.
- **Self-admitted unverifiability, acted on late.** At seq203 the agent noted it "can't verify the result myself" (Builder is web-only/HITL) — the exact signal to stop — but continued the STIX/dangling-edge loop for several more turns before the human forced the pivot.
- **Jargon leakage.** "SSOT", "you author this once" confused the human (seq47); agent conceded "poor wording on my part" (seq50). Cost a round-trip on a plumbing concept.
- **Assumption over-reach.** Early baseline imported Appendix A's invited assumptions (Azure Pipelines/PATs, unhardened VDI) that the human explicitly rejected (seq28, seq47: "stay in your lane"). Anchored on the appendix's suggested framing rather than eliciting.
- **Coverage gap found only in a late touch-up (seq275):** 4 of 10 scenarios (reputation, third-party oversight, situational awareness, accountability — the governance ones) never made it into any visual, living only in the control table. Not caught during the main build.

## Where grilling / wayfinder would have helped
- **Stop-loss on the Builder.** A wayfinder checkpoint at seq178 ("is the target render even achievable, and can you verify it?") would have surfaced the HITL/unverifiable wall before the multi-turn STIX debugging. The agent had the evidence at seq203; it needed a trigger to act on it.
- **Verifiability as a gate.** Grilling "how will you confirm this output is correct without a human in the loop?" would have pre-empted committing to a web-only GUI as an automation target.
- **Assumption elicitation before baseline.** A grilling pass on Appendix A's "invited assumptions" (which are GIVEN vs which are the org's actual posture?) would have avoided the seq28/47 rework.
- **Scope/coverage check at build entry.** "Are all 10 scenarios represented visually, or only the ones that fit the attack-path pattern?" catches the governance-scenario gap at the start, not as a retrofit.
- **Vocabulary check.** Wayfinder-style "define terms in the human's language" would have caught SSOT jargon.

## Salvage (reusable for the AI practice + NCF-I)
- **SSOT-emitter pattern** is the durable asset: one canonical threat-model file -> deterministic emitters for (a) architecture diagram, (b) Attack Flow STIX, (c) Navigator heatmap, (d) control table. Directly reusable as a threat-modelling method/template. Files: `ncf_threat_model/build/*.py`, `RUNBOOK.md`, `README.md`.
- **Parallel tool-scout fan-out** (8 sub-agents, one per candidate, benchmark-scored against human reference images) is a clean reusable evaluation harness for any "pick a tool" decision — pairs well with the financial exemplar's threat-model-agent prompt set.
- **Deploy-vs-instruct triage** (agent-deployable CLI/pip/Docker => automate + capture runbook; GUI/HITL => write human steps, don't claim install) is a good general operating rule to lift into practice guidance.
- **Attack-path-over-architecture convention** (vendor icons + dashed trust-boundary swimlanes + numbered step-badges keyed to a companion table; threat content NOT drawn into the picture) — validated visual standard worth codifying.
- **Windows rendering recipe:** `resvg` static binary for SVG->PNG to avoid the libcairo/cairosvg/svglib failure mode.
- **Anti-pattern to encode:** do not target human-only GUIs (e.g. Attack Flow Builder) as automation endpoints; use the `af` CLI (`af validate` full STIX 2.1, `af graphviz` canonical render, `af matrix` overlay) instead. The GUI's edge/layout is upstream-broken (issue #149).
